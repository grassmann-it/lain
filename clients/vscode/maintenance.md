# Local VS Code model groups maintenance

AP4 maintains one explicitly pinned Linux x64 build of `openai.chatgpt`:
Original `26.1021.22027`, local package `26.1021.22028`, display name
`Codex (Lain local groups)`. The publisher/name remain `openai`/`chatgpt`, so
the existing extension storage identity is retained. The local package is an
unsigned Lain adaptation, not an official OpenAI release. Preparing it does
not establish native qualification or install it.

The implementation is [vscode_groups.py](../../scripts/clients/vscode_groups.py).
Its transformer is the separately maintained
[vscode_groups_patch.py](../../scripts/clients/vscode_groups_patch.py), called as
`prepare_tree(source: Path, dest: Path) -> dict`. The maintenance layer owns
packaging, backups and receipts; it never launches Codex, calls a provider,
changes settings/auth/globalState, edits the extension registry directly, or
reloads a window. Use Python 3.11+ on Linux, with sufficient disk space for two
full trees and two VSIX files.

## Prepare a complete candidate

Use a trusted, complete input hash manifest prepared from the qualified
Original. Its shape is:

```json
{
  "schemaVersion": 1,
  "extensionId": "openai.chatgpt",
  "version": "26.1021.22027",
  "targetPlatform": "linux-x64",
  "files": {"package.json": "FULL_SHA256", "EVERY_OTHER_ORIGINAL_FILE": "FULL_SHA256"}
}
```

`files` must contain every regular file, including `.vsixmanifest`, all bundled
runtimes/platforms, helpers, resources and licenses. The five fixed identifiers
in `vscode_groups.PINS` must additionally match their independently recorded
original hashes; replacing the supplied manifest does not admit a new build.
Directories, modes, sizes and hashes are captured in the bundle manifest.
Links, hardlinks, special files, unsafe ownership/permissions and changed reads
are refused. A new build needs separate qualification and source changes.

```sh
python3 scripts/clients/vscode_groups.py prepare \
  --source /absolute/original-extension \
  --input-manifest /absolute/input.json \
  --bundle /absolute/new-bundle
```

The destination must not exist. Preparation uses a private sibling directory,
verifies an independent complete `original/` backup, transforms into
`candidate/`, and creates deterministic `original.vsix` and `candidate.vsix`.
Only the designated JavaScript locations and local package labels may change;
all original runtime files and other resources remain identical. The package
and VSIX identity get the local version. The transformer may add its
`lainLocalModelGroups` marker; maintenance also binds original tree provenance
in `x-lain-local-groups`. Foreign complete bundles stay outside this repository.

`manifest.json` records complete original/candidate inventories, package hashes,
input pins and the transform report. `transform.files` describes the transform
output *before* maintenance applies packaging metadata; `candidate` describes
the exact final tree. `maintenancePatchHelperSha256` binds the helper source
actually executed, and its reported source pins must match the copied adapter
bytes. The original backup retains the original package bytes,
including its installed `__metadata`. Candidate installation metadata is
generated by VS Code. Preparation publishes the complete directory with Linux
`RENAME_NOREPLACE` and returns its `manifestSha256` for review. Existing targets
are never replaced. A failed preparation publishes no bundle.

For shared qualification work, hold the same exclusive runtime lane lock around
large hashing/compression and native work:
`~/.cache/lain-verification-lane.lock`. This is separate from the bundle's
own `.maintenance.lock`. Do not run native GUI qualification concurrently with
another lane owner.

## Standard VS Code package selection

Read-only inspection of the installed VS Code 1.143.1
`resources/app/out/vs/code/node/cliProcessMain.js` establishes these concrete
implementation details:

- Local `installVSIX` supplies `installGivenVersion: true`, producing
  `pinned: true` and `source: "vsix"` in the selected extension metadata.
- `createInstallExtensionTask` constructs local VSIX keys from extension ID and
  version, without a target platform. The local directories therefore are
  `openai.chatgpt-26.1021.22028` and `openai.chatgpt-26.1021.22027`, even though
  these particular package contents are pinned to Linux x64. The original
  gallery directory ends in `-linux-x64`.
- Extraction selects the ZIP's `extension/` subtree. Our package retains
  `.vsixmanifest` there and also includes standard root VSIX metadata.
- Reinstalling an existing version can delete that version's directory through
  `deleteExtension` or `extractUserExtension`. Maintenance therefore refuses
  *any* existing destination, including an intact old installation. `--force`
  only bypasses VS Code's version downgrade confirmation; our preconditions
  prevent it being used for a blind overwrite.

The local version requires exact native qualification; its presence alone is
not a promise that an already running host has activated it. There is one
selected `openai.chatgpt` record in `extensions.json`. The old host may continue
using its preserved old resources until an explicit user reload. A native test
must establish this behavior before production installation. Retained inactive
folders are not treated as a second selected extension.

## Qualify the exact bytes

Native qualification writes an actual evidence report with this schema:

```json
{
  "schemaVersion": 1,
  "kind": "lain-vscode-groups-native",
  "result": "passed",
  "manifestSha256": "EXACT_MANIFEST_FILE_SHA256",
  "candidateVsixSha256": "EXACT_CANDIDATE_VSIX_SHA256",
  "candidateTreeSha256": "DIGEST_OF_MANIFEST_CANDIDATE_INVENTORY",
  "checks": {
    "originalActiveBeforeInstall": true,
    "originalTreePreserved": true,
    "singleSelectedRecord": true,
    "noAutomaticReload": true,
    "candidateActiveAfterManualReload": true,
    "rollbackOriginalAfterManualReload": true,
    "userStatePreserved": true
  }
}
```

`candidateTreeSha256` is `vscode_groups.digest(manifest["candidate"])`, using the
module's sorted, indented, UTF-8 JSON encoding with a final newline. Additional
native observations may be included. Every required check must be the JSON
boolean `true`, backed by the actual isolated original → candidate → original
run. An offline mock or a development-extension-path smoke test cannot provide
the installation/reload assertions. Do not manufacture passing evidence from
the offline tests.

`noAutomaticReload` must establish that the old running host still uses the
Original code after installation and before manual reload. An unchanged process
PID or preserved files alone does not establish this; observe the active
extension path/code as well as the selected disk record.

```sh
python3 scripts/clients/vscode_groups.py qualify \
  --bundle /absolute/bundle --evidence /absolute/native-evidence.json \
  --expect-manifest-sha256 REVIEWED_MANIFEST_SHA256
```

This validates the exact package/tree/manifest binding and runtime assertions,
then atomically publishes a separate `qualification.json`. It leaves
`manifest.json` and its reviewed hash unchanged. Existing qualification receipts
are not overwritten. The report is a local attestation by its author, not a
signature or an independent verification of claimed native observations.

## Plan, install, inspect and roll back

```sh
python3 scripts/clients/vscode_groups.py status \
  --bundle /absolute/bundle --extensions-dir /absolute/extensions

python3 scripts/clients/vscode_groups.py install \
  --bundle /absolute/bundle --extensions-dir /absolute/extensions \
  --user-data-dir /absolute/vscode-user-data --code /absolute/trusted/code \
  --expect-manifest-sha256 REVIEWED_MANIFEST_SHA256
```

Without `--apply`, install/rollback perform read-only preflight and return the
exact CLI command. `--apply` requires the reviewed manifest hash. Production
install additionally requires a valid qualification receipt. Native fixtures
may explicitly supply `--isolation-root /absolute/private-root`; both extension
and user-data directories must be children of that protected directory, outside
the default production locations. HOME and CODEX_HOME are never reassigned.
The isolation option is an explicit fixture designation, not a sandbox.

The applied command uses `code --install-extension PATH.vsix --force` with
explicit extension/user-data directories, and
`--do-not-include-pack-dependencies` to avoid adding extension packs/dependencies.
Machine scope is preserved with `--do-not-sync` when already set. Inherited
remote CLI routing hooks are removed for this explicitly local operation.
Named profiles containing Codex require separate qualification and are refused.

Maintenance records a durable append-only intent, runs the CLI, and verifies
the selected record, full selected package, preserved prior runtime trees,
scope flags and unrelated extension records. It neither uninstalls Codex nor
deletes retained trees. Runtime and license hashes must still match the bundle.
VS Code's mutable `package.json.__metadata` is the only content normalization;
local VSIX metadata may use platform `"undefined"` and refresh gallery metadata.
Extension ID, settings paths and globalState identity remain unchanged.

A successful installation returns `code: "reload-needed"`; no reload is sent.
Status also reports `runtimeActivation: "not-observed"`. `readyForGroups` means
the selected disk package matches a qualified candidate, not that a currently
running host has switched. Without qualification it remains false. An unknown
version, changed resource, invalid receipt or incomplete transaction reports
`maintenance-required` and never claims readiness.

```sh
python3 scripts/clients/vscode_groups.py rollback \
  --bundle /absolute/bundle --extensions-dir /absolute/extensions \
  --user-data-dir /absolute/vscode-user-data --code /absolute/trusted/code \
  --expect-manifest-sha256 REVIEWED_MANIFEST_SHA256 --apply
```

Rollback installs the backed-up Original as its own local VSIX under the same
extension ID and rechecks its full resources. It does not require native
qualification (or a valid qualification receipt) to recover a checked original.
It refuses an already existing
destination and retains the candidate for any old session. Gallery-original
bytes and the complete backup remain preserved. A successful rollback also
needs the user's explicit reload to affect a running host. Repeated cycles
with retained destination directories require inspection; no automatic cleanup
or overwrite is performed.

## Concurrency and interrupted operations

Preparation publishes atomically without replacement. Mutations use a private,
owned, single-link `0600` no-follow flock. Inputs are rechecked while locked;
unknown selected updates and preexisting destinations abort before invoking the
CLI. Status acquires no lock and writes nothing; it describes a checked snapshot.
Other installers do not share this lock. Do not run an updater or another package
installation against these directories concurrently. The external CLI's registry
and package operations are not a filesystem compare-and-swap transaction.

Each `transaction-*/intent.json` retains the original registry and operation
binding; `completed.json` is written only after all checks pass. A timeout kills
the CLI process group and leaves the intent for inspection. There is no silent
retry, reload, updater adoption or automatic recovery. Incomplete operations
remain maintenance-required even if a later explicit rollback changes the
selection; inspect their receipts rather than deleting evidence. A changed
Original backup or unknown current build prevents rollback.

Offline verification:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover \
  -s tests/vscode-groups -p test_maintenance.py -v
```

These disposable fixtures cover copying/packaging, protected resources,
installation/rollback plans, registry selection, qualification binding,
interruption, locks, concurrent publication and unsafe inputs. They do not
qualify the real VS Code extension host or the bundled picker.
