# Profile application and Codex artifact recovery

Run `dotnet run --project tests/profile-application/ProfileApplication.Tests.csproj`.
The fixtures use an isolated temporary state directory and a synthetic Core lifecycle;
they do not read credentials, call providers, start the installed service or modify
ordinary Codex configuration. Actual stream-drain qualification belongs to the Core
quiescing tests, not this synthetic delegate fixture.

The suite covers separate save/apply, all pending effective route/account changes,
profile-only changes, disabled defaults, stale revisions, serialized application,
queued cancellation, a refused stream drain, metadata write failure, interrupted
commit, explicit retry, exact runtime generation and stale/interrupted client export.
It checks retained old catalogs, content tampering and symlink rejection.

## Recovery contract

A new successful apply requires a matching profile, revision and generation in the
runtime and active metadata, the applied repository revision, and a completed
application journal. Startup must call `RequireCompletedRuntime()` before starting
the Core. An incomplete journal or mismatched metadata never proves active success.

The application first drains requests through the lifecycle delegate. A refused
or canceled drain leaves the old runtime files and their commit proof intact only
when the lifecycle callback has confirmed that the old Core accepts new requests
again. Reopening requires an authenticated activity read with `draining=false`;
a failed DELETE response alone cannot prove either success or failure. If admission
cannot be confirmed, the callback sets its readiness diagnostic and throws
`ProfileDrainRecoveryRequiredException`. The service retains a recovery marker,
leaves prior runtime files byte-identical and lets active streams finish. Normal
startup/restart cannot bypass that marker; an explicit apply can recover.
After drain/stop, request cancellation no longer cancels publication. A later
failure stops the new Core and records `recovery-required`. The user recovers by
previewing the current saved profile and explicitly applying that revision again.
This writes a fresh runtime from current credentials; it never restores older
rotated credentials. Configuration saves are not rolled back. No route toggle
implicitly invokes apply. All gateway clients still share one applied profile.

Codex installation atomically replaces `lain.config.toml` with a configuration
referencing a private immutable catalog generation under `.lain-artifacts`.
Existing generations are retained so already running clients can continue to read
their catalog. `lain.models.json` is only a compatibility copy. New generated
configurations do not reference it. The private journal and content hashes detect
interruption before or after the configuration commit. `Inspect` reports
`recovery-required` until explicit re-export/install repairs bookkeeping. Compare
its installed profile and revision with the host's applied identity to detect a
stale export; an absent identity is unknown, never implicitly current.

A crash can leave unreferenced private generation files. There is deliberately no
automatic retention/deletion policy. File contents are flushed before atomic
rename; sudden storage-device or filesystem failure still requires filesystem
recovery, and the checks do not claim protection against a malicious local user
who can replace both artifacts and all integrity metadata.

## Preserving an older applied runtime

`legacy-preserved` is an explicit read-only compatibility state. It requires both
legacy metadata files, matching applied revisions, `runtime.valid=true`, no
`generationId` property in either document, and no application marker (including
an invalid file, directory or dangling symbolic link). It permits startup from the
existing runtime even if the older metadata does not prove its profile identity.
Active profile identity stays unknown until independently proven. Missing or null
legacy identity fields remain unknown; contradictory explicit identities and
non-string/blank identities are rejected. A desired
revision newer than the applied revision remains pending; this check never
resolves it, invokes apply or writes runtime/configuration metadata.

Any new generation or application marker disables this fallback. Partial new
publication, invalid runtime, inconsistent applied revisions and missing active
metadata continue to require recovery. This compatibility path does not weaken
the complete transaction proof for runtimes generated by the new application flow.

## Local evidence, 2026-10-24

On the ST-02 source commit, Linux x64 fixtures passed: profile-application 43,
applied-profile 104, codex-gateway-profile 14 and client-cli 220 checks; the models
CAS/persistence/privacy/export regression also passed. Tests ran serially. Existing
non-RID fixture lockfiles were kept unchanged; RID qualification used temporary
per-project lockfiles where needed. The new suite has its own checked-in lockfile.
These results do not claim real provider calls, installed service acceptance or
a real active stream drain; the integrated Core quiescing gate needs its own proof.

The follow-up compatibility/drain review expanded the profile suite to **92 passing
checks**; the **104 applied-profile checks** also passed again on Linux x64 in
locked restore mode. Added proof covers preserved desired11/applied2 legacy
startup without any file/configuration writes, explicit unknown identity,
contradictory/invalid identity rejection, generation/marker refusal, and uncertain
drain admission retaining a recovery marker while leaving streams/runtime files
untouched. These remain synthetic lifecycle checks; authenticated Core admission
confirmation is separately owned and qualified by the integrated lifecycle tests.
